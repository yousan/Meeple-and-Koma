# 仕様書：ameyaka（傘の持ち忘れ防止アプリ）

最終更新：2026-11-14 ／ 開発期間：1週間 ／ デザイン：Figma（PC幅の4画面を作成済み）

> `（仮）` と書かれた値は初期案です。実機で試しながらチームで調整してください。

## 1. 目的

傘の持ち忘れ・置き忘れによる「ずぶ濡れ」をなくす。
やらかし集 No.4（天気を見ずに出て濡れた）と No.10（傘を家とコンビニに忘れた）を解決する。

## 2. スコープ

| フェーズ | 内容 | 優先度 |
|---|---|---|
| 1 | 天気取得、雨予報の通知（出発前・帰宅前）、通知設定、通知履歴 | 必須 |
| 2 | 傘の状態の検知（ESP32など）と強化通知、「傘の状態」画面 | できれば |
| 3 | スマートタグ併用の案内（置き忘れ通知はタグ側アプリ） | 余裕があれば |

**今回外すもの**：「傘を持った」ボタンと記録（デザインにないため。必要なら将来追加）、アプリからのBluetooth直接検知（Web/PWAでは制約が大きいため）

## 3. 共通仕様

- アプリ名：ameyaka、キャッチコピー：「傘を忘れない。」
- ナビゲーション：ホーム／設定／通知履歴／傘の状態
  - PC幅：左サイドバー（デザイン済み）
  - **スマホ幅：画面下のタブバー**（ホーム・通知履歴は作成済み。設定・傘の状態は未作成）
- サイドバー（PC幅）の左下に「今日の（地域名）　天気・降水確率」のミニ表示
- ログインなし（ヘッダー右上のアイコンは、アカウント機能を作らないなら削除または装飾扱い）
- 地域は現状「渋谷区」の固定表示。**変更方法は未決**（設定に項目を追加するか、位置情報で自動取得）

## 4. 画面仕様

### 4.1 ホーム

| 要素 | 内容 |
|---|---|
| ヘッダー | 日付と曜日、あいさつ（時間帯で切り替え） |
| 天気カード | 地域名、現在の気温、天気の概要（例：午後から雨）、更新時刻、降水確率（数値とバー）、降り始めの目安時刻（例：15時ごろから降り始める予報です） |
| 傘の判定カード | 「持っていこう／今日は傘が必要です」と理由（例：帰宅時間に雨が予想されています）。雨が予想されない日は「今日は傘は不要です」（文面は要デザイン）。タップで傘の状態画面へ |
| 今日の予定 | 自宅を出発（時刻・通知が届く時刻）、会社を出発（同）。「設定を変更」リンクで設定画面へ |
| 傘の状態カード | 例：「傘は玄関にあります」と接続状態。タップで傘の状態画面へ |

### 4.2 設定（通知設定）

| 要素 | 内容 |
|---|---|
| 通知タイミング | 出発前通知・帰宅前通知・強化通知のオン／オフ切り替え。有効な件数をバッジで表示 |
| 時刻と対象時間帯 | 外出時刻と通知時刻（初期値 08:30／08:00）、帰宅時刻と通知時刻（初期値 18:30／18:00）。「天気の判定対象」は外出時刻〜帰宅時刻を自動表示 |
| 通知する降水確率 | スライダー（10%〜90%）、**初期値40%以上**。しきい値未満の日は通知しない旨の説明を表示 |
| 通知の最適化 | 同じ内容を何度も通知しない（下記4.5の「通知の重複防止」参照） |
| 保存ボタン | 「この内容で保存」 |

天気APIの連携状態（「天気API連携中」）をバッジで表示する。

### 4.3 通知履歴

| 要素 | 内容 |
|---|---|
| ヘッダー | 件数バッジ、説明文 |
| フィルタ | すべて／出発前／帰宅前／強化通知 |
| 一覧 | 種類タグ、タイトル、本文、日時（当日は「今日 8:00」、それ以前は「6月14日 18:00」形式）。新しい順 |
| フッター | 「晴れの日はお知らせしません」の説明 |

0件のときの空の状態は未デザイン（要追加）。

### 4.4 傘の状態

| 要素 | 内容 |
|---|---|
| ヘッダー | 画面名、説明文、更新ボタン（右上） |
| 状態カード | 接続バッジ（タグ接続中）、傘のイラスト、最終確認時刻、状態の文言（例：傘は玄関にあります）、検知方法のチップ（例：傘立てで検知） |
| 詳細 | 接続（良好など）、バッテリー（%）、登録場所（自宅など） |
| 登録中のタグ | タグ名（例：いつもの傘）、型番、接続状態 |
| デモ状態の切り替え | 傘の「あり／なし」を手動で切り替えるボタン。ハードが間に合わない場合のデモ保険、かつ開発時の動作確認用 |

注意書き（現状「スマートタグの位置情報から自動で判定されます」）は、実際の検知の仕組みに合わせて書き直す。

### 4.5 追加が必要な画面・状態

**作成済み（スマホ幅 390×844）**：ホーム、通知履歴（帰宅前A・Bの両方を掲載）、通知の文面（ロック画面の通知3種）、iPhone導入案内（「ホーム画面に追加」の手順と通知許可）

**未デザイン**：

- 設定、傘の状態のスマホ版（下部タブバー）
- 通知履歴が0件のときの空の状態
- 天気の取得に失敗したときのエラー表示
- 通知がオフのときの警告表示

## 5. 通知仕様

### 5.1 通知の種類

| 種類 | タイミング | 条件 | 文面（デザインより） |
|---|---|---|---|
| 出発前通知 | 設定した通知時刻（初期値 8:00） | 外出〜帰宅の時間帯の降水確率がしきい値以上 | 「午後から雨が降る予報です」「降水確率は70%。傘を忘れずにお持ちください。」 |
| 帰宅前通知（A：傘が会社にあるとわかる日） | 設定した通知時刻（初期値 18:00） | 帰宅時間帯の降水確率がしきい値以上 ＋ 傘の場所が「会社」と判定できる | 「帰宅時間に雨の予報です」「会社に置いてある傘をお忘れなく。」 |
| 帰宅前通知（B：傘の場所がわからない日） | 同上 | 帰宅時間帯の降水確率がしきい値以上 ＋ 傘の場所が「会社」と判定できない | 「帰宅時間に雨の予報です」「降水確率は70%。傘はお持ちですか？」 |
| 強化通知 | 出発時刻の10分前（仮、例：8:20） | 雨予報 ＋ 傘が玄関（傘立て）にある | 「傘はまだ玄関にあります」「まもなく出発時刻です。傘をお持ちください。」 |

- 雨が予想されない日（しきい値未満）は通知しない
- 降水確率が高めのときは「折りたたみ傘がおすすめです」のように、文面を出し分ける案もある（デザインの履歴例にあり）
- **帰宅前通知は2パターンに出し分ける**（決定）
  - 傘の場所が「会社」と判定できる場合だけ、パターンA「会社に置いてある傘をお忘れなく。」を使う
  - それ以外（センサー未導入、データなし、判定不能）は、パターンB「降水確率は○%。傘はお持ちですか？」を使う
  - パターンAの判定は、傘の状態データの `location` が `office` のときのみ。会社側に検知器がなければ、実質パターンBのみになる
  - タイトル「帰宅時間に雨の予報です」は共通。通知履歴にも、そのとき出した文面をそのまま残す

### 5.2 判定ルール

- 判定対象：設定した外出時刻〜帰宅時刻の時間帯
- 降水確率のしきい値：初期値40%（設定で10〜90%）
- 時間ごとの降水確率から「降り始めの目安時刻」を求め、ホームに表示する

### 5.3 通知の重複防止（通知の最適化）

- 同じ種類の通知は、1日1回まで（仮）
- 強化通知は、傘が玄関から取り出された時点で送らない

## 6. 技術構成

| 項目 | 内容 |
|---|---|
| アプリ形態 | PWA（HTML/JS、またはReact） |
| 天気API | Open-Meteo（キー不要）、または気象庁のデータ |
| サーバー | Firebase（Firestore + Cloud Functions）またはSupabase |
| 通知 | まずLINE / Discordで動作確認 → 余裕があればWeb Push |
| IoT受信 | サーバーのHTTPエンドポイント |

### 6.1 端末対応の注意（iPhoneが主）

- iPhoneでは、**Safariで開いて「ホーム画面に追加」したPWAのみ**Web Pushが届く（iOS 16.4以降）
- 初回起動時に、ホーム画面への追加手順と通知許可を案内する画面を用意する
- 動作確認は**iPhone実機**で行う（Android担当者の端末だけでは確認できない）
- 通知が不安定な場合に備え、LINE / Discord通知を代替手段として残す

## 7. IoT連携仕様（フェーズ2）

### 7.1 データ形式（ハード → サーバー）

```json
{
  "device_id": "umbrella_stand_01",
  "umbrella_present": true,
  "battery_percent": 82,
  "connection": "good",
  "location": "home",
  "timestamp": "2026-11-14T07:30:00+09:00"
}
```

- 傘の状態が変わったときに、HTTP POSTで送信する
- 「傘の状態」画面の表示項目（バッテリー、接続、登録場所）に必要なため、`battery_percent`・`connection`・`location` を追加した。`location` は `home`（自宅・玄関）、`office`（会社）、`unknown` のいずれかとし、帰宅前通知の出し分け（パターンA/B）にも使う。ハード担当が送れない項目は、画面から外すか固定表示にする
- 認証：簡易トークン（ヘッダーで送る）を想定（詳細は未決）

### 7.2 アプリ側の動作

- 「傘あり ＋ 雨予報 ＋ 出発時刻が近い」で強化通知を出す
- 「デモ状態を切り替える」ボタンで、サーバーへ疑似データを送る（ハードが間に合わなくてもデモが成立する）

### 7.3 ハード担当への確認事項

- 傘の有無の検知方法（距離・重量・スイッチ・BLEタグなど）
- バッテリー値と接続状態を送れるか
- 使用マイコン（ESP32など）と通信方式

## 8. 置き忘れ防止（スマートタグ併用・フェーズ3）

置き忘れ通知は、**タグ側のアプリが出す**。本アプリはタグの状態を読み取らない。

| 項目 | 内容 |
|---|---|
| 本アプリの役割 | 初回の設定案内、通知文面での呼びかけ |
| タグの選択 | チームの端末がiPhone中心なら**AirTag**が有力。AndroidとiPhone両方で使いたい場合は**Tile**（機能や料金プランは購入前に要確認） |
| 注意 | AirTagはiPhone専用。Android担当者の端末では置き忘れ通知を確認できない |
| デモ前の確認 | 実際に傘から離れたときの通知タイミングを、iPhone実機で確認する |

発表では「市販スマートタグと連携した運用」と説明し、IoTとして見せるのは傘立てなどのセンサー部分とする。
